# セッションの進め方

## 実行前

記録係は対象の版、開始URLまたは資料、画面幅、入力方法、ログイン状態、テストデータ、許可範囲を保存する。パスワード・トークン・個人情報は出力しない。

ペルソナ役へ渡すのは、その人のカード、タスクの目的、開始状態、許可範囲だけ。設計者の正解経路、他ペルソナの発見、事前の改善案を渡さない。達成条件は評価側で照合する。

標準の操作上限はタスクあたり20操作、同じ行き詰まりの再試行は2回まで。対象に合わせて実行前に変更してよい。この上限は作業の停止条件で、人間の忍耐力の実測ではない。

## 1ステップの記録

1. **観察**: 現在の画面・表示・利用可能な操作を確認し、証拠IDを付ける。URLだけで表示を再確認できない場合は画面やツール出力も残す。
2. **選択**: そのペルソナが知り得る範囲で、次の操作と短い理由を記録する。内的な思考の逐語記録は求めない。
3. **実行**: 選んだ操作を一つ進める。結果の画面や状態を確認するまでは成功としない。
4. **照合**: 期待した結果と実際の結果を区別し、進む・戻る・助けを探す・停止を選ぶ。

利用者に見えない内部データ、ソースコード、隠れたリンクで迂回しない。DOM等が操作ツールに必要でも、見える導線に対応した操作に限る。コード調査で原因を確認する場合は、セッション後の専門家分析として別記する。

初心者の見つけやすさを確認するときは、各節目で「次に何をすべきか分かるか」「操作を見つけられるか」「表示から結果を想像できるか」「実行後に進捗が分かるか」を評価側で確認する。否定的な答えをペルソナに強制しない。

## 状態とツールの制約

- ペルソナごとに開始状態を戻す。作成済みデータや学習済み導線を引き継ぐ場合は、継続利用のシナリオとして明示する。
- 新しいタブでもCookieやアカウントは共有され得る。分離できなければ順次実行し、状態の共有範囲を記録する。
- CAPTCHA、ログイン手段不足、操作ツール非対応は `blocked`。迂回を試みず、サービスの使いにくさに変換しない。
- 未許可の購入・外部送信等の直前で止まった場合も `blocked`。依頼範囲内で確認できた部分は残す。
- `artifact` では想定する操作を `proposed` として記録できるが、実行したとは書かない。全タスク結果は `not_run`。静的に分かる表示上の問題は評価可能。
- `interactive` の途中から資料に切り替えるときは、別の資料セッションを作って全体を `mixed` にする。

## タスクの終わり

| 結果 | 意味 |
| --- | --- |
| `success` | 事前の達成条件を満たす結果状態をUIで確認した |
| `partial` | 定義した成果の一部だけを結果状態で確認した |
| `failure` | 実行したが、達成条件を満たせない結果を確認した |
| `abandoned` | 事前の離脱条件または操作上限に達した。仮説上の離脱と表示する |
| `blocked` | 環境・認証・許可・ツール等の制約で判定できない |
| `not_run` | 未実行、割当のみ、資料レビュー |

`success`/`partial`/`failure`/`abandoned` は操作と結果の証拠を必須にする。`blocked` には制約の説明を付ける。未割当の組合せもレポートの割当表で区別する。

機械の操作回数や実行時間は必要に応じて記録できるが、人間の所要時間・認知負荷の実測として扱わない。推定の感情、満足度、離脱意向は仮説と表示する。実際に話した人がいない引用を、利用者の声として提示しない。
